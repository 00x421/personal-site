fix(rail): 拖拽文章轨道后自己回弹

用户报「拖拽文章的那个条，会自己回弹」。查下来是两个机制叠加，都在强制
把轨道拉回卡片起点，其中 JS 那个是主凶。

一、rail-scroller.tsx 里的 settle 挂在 scroll 上（主因）
它监听 scroll，停止滚动 220ms 后把 scrollLeft 校正到最近的卡片起点。
于是任何一次手动拖拽，松手后轨道都会自己动一下——而且因为是延迟触发 +
smooth 动画，看起来完全像「轨道自己弹回去了」。

实测（线上）：把 scrollLeft 设到 438px（卡片 2 起点 335、卡片 3 起点 669），
900ms 后自己被改成 334px。

改成只在 resize 时校正。原注释说这段是为了修「resize / 个别手势下停在切字的
中间态」，那个诉求在 resize 场景下依然成立（卡片宽度是视口相关的，resize 后
旧的像素 scrollLeft 会错位），所以保留能力、只摘掉 scroll 触发。
实测：停在 500 → 触发 resize → 回到 335 ✓

二、scroll-snap-type 从 mandatory 改成 proximity
`mandatory` 在物理上不允许轨道停在非吸附点——连脚本赋值都会被浏览器立即
纠正。纯 CSS 对照实测（克隆节点，无 JS 干扰）：

  目标 350 → 335    目标 438 → 335    目标 500 → 335    目标 620 → 669
  改成 proximity 后：
  目标 350 → 335    目标 438 → 335    目标 500 → 500 ✓  目标 620 → 669

proximity 只在靠近吸附点时轻轻对齐，中间位置可以自由停留；「快速翻到下一张」
的手感与 mandatory 一致。注意 mandatory 那个「读到半张卡就停不住」的问题，
正是当初加 settle 的原因——两个机制互相掩盖了对方的毛病。

顺带收益：左右按钮现在每次正好翻一张卡（0 → 335 → 669 → 974，回退对称），
渐隐遮罩 data-at-start/end 同步正确。

验证（线上）：6 个位置全部 immediate === after，movesAfterStop 0 次。
npm test 76/76、tsc 零错误、oxlint 零告警。
